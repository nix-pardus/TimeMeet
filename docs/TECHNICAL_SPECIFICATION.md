# Техническое задание: TimeMeet

## 1. Цель проекта

TimeMeet — бесплатное open-source веб-приложение на русском языке для согласования времени созвонов и встреч групп людей.

Основной сценарий состоит из двух фаз в рамках одной встречи:

```text
Свободная сетка → анализ доступности → выбор лучших вариантов → финальное голосование → итоговое время
```

Сначала участники отмечают свою доступность в свободной временной сетке. Затем система рассчитывает лучшие общие интервалы, организатор выбирает несколько вариантов, и участники окончательно голосуют по фиксированным слотам.

## 2. Основные принципы

- Бесплатное использование.
- Open source под лицензией MIT.
- Голосование без регистрации по ссылке.
- Поддержка часовых поясов.
- Все даты и время хранятся в UTC.
- Часовые пояса хранятся в формате IANA, например `Europe/Moscow`.
- Экспорт результатов в `.ics`, CSV и JSON.
- Никакого vendor lock-in.
- Минимальные расходы на инфраструктуру.
- Донаты только через внешние сервисы.

## 4. Состояния и фазы встречи

### 4.1. Статус встречи

```text
Draft      — черновик
Active     — активная встреча
Closed     — голосование завершено
Archived   — встреча архивирована
```

### 4.2. Фаза встречи

```text
AvailabilityCollection — сбор доступности в свободной сетке
FinalSlotSelection     — финальное голосование по фиксированным слотам
```

При создании:

```text
Status = Active
Phase = AvailabilityCollection
```

`FixedSlots` больше не является самостоятельным режимом создания встречи. Фиксированные слоты появляются только после анализа свободной сетки.

## 5. Модель данных

### 5.1. User

Зарегистрированный пользователь:

- `Id` — PK.
- `Email` — уникальный email.
- `DisplayName`.
- `TimeZone`.
- `CreatedAt`.
- `IsDonor`.

### 5.2. Meeting

Встреча, которая проходит через несколько фаз:

- `Id` — PK.
- `ShortCode` — уникальный код длиной 8–10 символов.
- `OwnerToken` — токен организатора.
- `Title`.
- `Description` — nullable.
- `OrganizerId` — nullable FK к `User`.
- `OrganizerName`.
- `TimeZone` — часовой пояс организатора.
- `ParticipationMode` — `LinkOnly` или `InvitedList`.
- `Phase` — `AvailabilityCollection` или `FinalSlotSelection`.
- `Status`.
- `Deadline` — nullable.
- `AllowAnonymous`.
- `AllowRegistration`.
- `GridStartDate` — `DateOnly`, дата начала в часовом поясе организатора.
- `GridEndDate` — `DateOnly`, дата окончания в часовом поясе организатора.
- `GridFrom` — `TimeOnly`, локальное время начала в часовом поясе организатора.
- `GridTo` — `TimeOnly`, локальное время окончания в часовом поясе организатора.
- `GridStepMinutes`.
- `SelectedTimeSlotId` — nullable FK к `TimeSlot`.
- `CreatedAt`.
- `ClosedAt` — nullable.
- `ArchivedAt` — nullable.

`OwnerToken` хранится в HttpOnly-cookie организатора сроком 30–90 дней. Cookie устанавливается после создания встречи и используется для доступа к панели управления. Если организатор очистил cookie или открыл встречу с другого устройства, восстановление доступа в MVP невозможно, поскольку email-рассылки и другие способы восстановления не входят в MVP. Организатор должен сохранить ссылку управления самостоятельно.

Поле `AvailabilityMode` для первоначального создания встречи больше не требуется.

### 5.3. GridCell

Ячейка свободной временной сетки:

- `Id` — PK.
- `MeetingId` — FK.
- `StartTime` — UTC.
- `EndTime` — UTC.

При создании встречи создаются ячейки на основе диапазона дат, часов и выбранного шага.

`GridStartDate`, `GridEndDate`, `GridFrom` и `GridTo` интерпретируются в часовом поясе организатора. После генерации фактические границы каждой ячейки сохраняются в UTC в `StartTime` и `EndTime`.

`GridCell` не удаляется при архивации встречи. Используется soft-delete на уровне встречи: устанавливается `Meeting.Status = Archived`, а обычные запросы исключают архивированные встречи и связанные с ними ячейки. Это сохраняет историю первой фазы для будущей аналитики.

Связанные `Availability` с `GridCellId` также сохраняются и не удаляются каскадно при архивации.

Индексы:

- `MeetingId`.
- `MeetingId + StartTime`.

### 5.4. TimeSlot

Фиксированный слот финального голосования:

- `Id` — PK.
- `MeetingId` — FK.
- `SourceGridCellId` — nullable FK к `GridCell`.
- `StartTime` — UTC.
- `EndTime` — UTC.

`TimeSlot` создаётся только после выбора организатором лучших ячеек свободной сетки.

### 5.5. Participant

Участник встречи:

- `Id` — PK.
- `MeetingId` — FK.
- `UserId` — nullable FK к `User`.
- `DisplayName`.
- `TimeZone`.
- `ParticipantToken`.
- `CreatedAt`.
- `UpdatedAt`.

`ParticipantToken` создаётся через `RandomNumberGenerator`, содержит 32 случайных байта и хранится в HttpOnly-cookie сроком 30–90 дней.

### 5.6. Availability

Отметка доступности участника:

- `Id` — PK.
- `ParticipantId` — FK.
- `GridCellId` — nullable FK к `GridCell`.
- `TimeSlotId` — nullable FK к `TimeSlot`.
- `Status`:
  - `Available`;
  - `IfNeeded`;
  - `Unavailable`.
- `CreatedAt`.
- `UpdatedAt`.

Ровно одно из полей `GridCellId` и `TimeSlotId` должно быть заполнено.

Это правило фиксируется на уровне PostgreSQL CHECK-ограничением:

```sql
CHECK (
	(GridCellId IS NOT NULL AND TimeSlotId IS NULL)
	OR (GridCellId IS NULL AND TimeSlotId IS NOT NULL)
)
```

На первой фазе используется `GridCellId`, на второй — `TimeSlotId`.

### 5.7. Invitation

Задел на будущее:

- `Id`.
- `MeetingId`.
- `Channel`.
- `Contact` — nullable.
- `DisplayName`.
- `Token` — nullable.
- `TokenExpiresAt` — nullable.
- `Status`.
- `SentAt` — nullable.
- `RespondedAt` — nullable.
- `ParticipantId` — nullable.
- `CreatedAt`.

В MVP сущность создаётся миграцией, но не используется.

## 6. Создание встречи

Страница:

```text
/create
```

Поля формы:

- Название встречи.
- Описание.
- Имя организатора.
- Часовой пояс организатора.
- Дата начала сетки.
- Дата окончания сетки.
- Время начала сетки.
- Время окончания сетки.
- Шаг сетки: 30 или 60 минут.
- Дедлайн голосования.
- Разрешить анонимное голосование.
- Разрешить регистрацию участников.

После отправки:

1. Валидируются даты, часы и часовой пояс.
2. Генерируется `ShortCode`.
3. Генерируется `OwnerToken`.
4. Создаётся встреча.
5. Создаются `GridCell`.
6. Встреча получает `Active + AvailabilityCollection`.
7. Организатор перенаправляется на панель управления.

При создании `Deadline` относится к фазе `AvailabilityCollection`. Дедлайн хранится в UTC, а вводится организатором в его часовом поясе.

Формы выбора фиксированных слотов при создании нет.

## 7. Голосование участника

URL:

```text
/m/{ShortCode}
```

### Первый вход

Показываются:

- название встречи;
- описание;
- имя организатора;
- дедлайн;
- поле имени;
- часовой пояс участника.

Часовой пояс определяется через:

```javascript
Intl.DateTimeFormat().resolvedOptions().timeZone
```

После продолжения:

1. Создаётся `Participant`.
2. Генерируется `ParticipantToken`.
3. Токен устанавливается в HttpOnly-cookie.
4. Пользователь возвращается на `/m/{ShortCode}`.

### Повторный вход

При наличии cookie:

- участник определяется автоматически;
- загружаются его прежние отметки;
- имя и часовой пояс берутся из базы.

## 8. Голосование в свободной сетке

Фаза:

```text
AvailabilityCollection
```

Показывается сетка:

- строки — даты;
- столбцы — часы;
- ячейки — `GridCell`.

Цикл статусов:

```text
Не отмечено → Свободен → Если нужно → Не могу → Свободен
```

Цвета:

- зелёный — `Available`;
- жёлтый — `IfNeeded`;
- красный — `Unavailable`;
- серый — не отмечено.

Изменения сохраняются автоматически с debounce 1–2 секунды.

Если `Deadline` истёк, новые отметки участников блокируются, но встреча не переключается автоматически. Организатор может открыть панель, увидеть уведомление «Дедлайн прошёл, выберите слоты для финального голосования» и вручную перейти к следующей фазе.

## 9. Расчёт лучших интервалов

На панели организатора доступна кнопка:

```text
Найти общие интервалы
```

Для каждой ячейки рассчитываются:

- количество `Available`;
- количество `IfNeeded`;
- количество `Unavailable`;
- список доступных участников;
- список недоступных участников;
- рейтинг интервала.

Приоритеты:

1. Все участники имеют статус `Available`.
2. Максимальное количество `Available`.
3. Минимальное количество `Unavailable`.
4. Максимальное количество `IfNeeded`.
5. Более раннее время.

Пример рейтинга:

```text
Score = AvailableCount * 100
	  + IfNeededCount * 20
	  - UnavailableCount * 100
```

Если полного пересечения нет, показываются лучшие варианты с пояснением количества подходящих участников.

## 10. Создание финального голосования

Организатор выбирает от 2 до 5 рекомендованных ячеек и нажимает:

```text
Создать финальное голосование
```

Система:

1. Создаёт `TimeSlot` на основе выбранных `GridCell`.
2. Переводит встречу в `FinalSlotSelection`.
3. Сохраняет прежних участников и их токены.
4. Сохраняет `Availability` с `GridCellId` как исторические ответы первой фазы.
5. Не переносит ответы первой фазы в `Availability` с `TimeSlotId`.
6. Требует от участника проголосовать заново по фиксированным слотам.
7. Оставляет прежнюю ссылку встречи.

При переходе в `FinalSlotSelection` организатор может установить новый `Deadline` для финального голосования. Если новый дедлайн не задан, финальная фаза считается открытой до ручного закрытия встречи.

Ответы первой фазы используются для истории, аналитики и отображения в панели организатора, но не влияют на результаты финального голосования. Финальные результаты рассчитываются только по новым `Availability`, связанным через `TimeSlotId`.

## 11. Финальное голосование

Фаза:

```text
FinalSlotSelection
```

Участник видит только выбранные фиксированные слоты и отмечает:

- `Available` — свободен;
- `IfNeeded` — если нужно;
- `Unavailable` — не могу.

Время отображается в часовом поясе участника.

Организатор видит для каждого слота:

- количество доступных участников;
- количество ответов «если нужно»;
- количество недоступных участников;
- процент согласия;
- список участников, которым слот подходит.

## 13. Завершение встречи

Организатор нажимает:

```text
Закрыть голосование
```

Система:

1. Проверяет выбранный финальный слот.
2. Записывает `SelectedTimeSlotId`.
3. Устанавливает `Status = Closed`.
4. Записывает `ClosedAt`.
5. Запрещает изменения голосов.
6. Показывает итоговое время всем участникам.

При архивации встреча переводится в `Status = Archived`. Архивация является soft-delete:

- `GridCell` не удаляются;
- исторические `Availability` с `GridCellId` не удаляются;
- `TimeSlot` не удаляются;
- финальные `Availability` с `TimeSlotId` не удаляются;
- `SelectedTimeSlotId` сохраняется;
- агрегированная статистика сохраняется.

Для исключения архивированных встреч используется глобальный query filter EF Core:

```csharp
modelBuilder.Entity<Meeting>()
	.HasQueryFilter(x => x.Status != MeetingStatus.Archived);
```

Связанные сущности, которые загружаются через встречу, также не должны отображаться в обычных пользовательских запросах. Для аналитики, админки и операций архивирования фильтр отключается через `IgnoreQueryFilters()`. Физическое каскадное удаление `GridCell` и связанных доступностей не применяется.

## 15. Безопасность

- `ShortCode` генерируется криптостойко.
- `OwnerToken` и `ParticipantToken` генерируются через `RandomNumberGenerator`.
- Cookie имеет флаги `HttpOnly`, `Secure` в production и `SameSite=Lax`.
- `OwnerToken` хранится в HttpOnly-cookie сроком 30–90 дней; восстановление доступа после потери cookie в MVP отсутствует.
- Все входные данные валидируются.
- Нельзя сохранить доступность для другой встречи.
- Нельзя менять голос после дедлайна.
- Нельзя менять голос закрытой встречи.
- Добавляется rate limiting на создание встреч.
- Создание участников ограничивается rate limiting по IP и максимальным количеством участников на одну встречу.
- В MVP устанавливается ограничение не более 100 участников на одну встречу. Защита от обхода ограничения через разные IP и браузеры не гарантируется.
- Формы защищаются от CSRF.

- Email-рассылки.
- Telegram-уведомления.

- Автоматические напоминания.
- Автоматические уведомления участникам о переходе во вторую фазу. В MVP организатор вручную переключает фазу и самостоятельно сообщает участникам о начале финального голосования по прежней ссылке.

- Микросервисная архитектура.
- Blazor WebAssembly.
- OAuth-провайдеры.

## 21. Критерии готовности MVP

MVP считается готовым, если:

- пользователь может создать встречу со свободной сеткой;
- участник может проголосовать без регистрации;
- время отображается в часовом поясе участника;
- организатор видит общую доступность;
- система находит интервалы, подходящие всем участникам;
- организатор может выбрать от 2 до 5 финальных слотов;
- встреча переключается в фазу финального голосования;
- участники голосуют за фиксированные слоты;
- организатор выбирает финальное время;
- встречу можно закрыть;
- итоговый слот экспортируется в `.ics`;
- ссылка встречи сохраняется на всех фазах;
- приложение запускается через `docker-compose up`;
- миграции создаются и применяются вручную через терминал;
- код опубликован под лицензией MIT.
